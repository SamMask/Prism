# 維護協議：怎麼安全地更新本資料夾的文件

適用對象：未來任何要修改本資料夾（母模板庫）文件的 LLM session，不分模型強弱、不分 Claude / Codex。
原則：這套制度的價值在於「可信」，不在於「多」。每次維護的目標是讓文件更短更準，不是更長。

## 1. 權限分級

**可以自行改（改完在回報中列出即可）：**

- 錯字、失效的檔名 / 路徑 / 章節引用、格式修正。
- 在 `AI-CODING-RULES-REFERENCE.md` 來源表新增紀錄。
- 把使用者明確口述的新教訓，按 §4 格式寫入對應母模板。
- `治理/LETTER-TO-FUTURE-SESSIONS.md` 的「交接區」段落（見該檔說明）。

**改之前必須先問使用者：**

- 刪除或重寫任何既有規則（精簡建議先列清單給使用者選，不要直接刪）。
- 更動硬邊界清單（000.txt、Prompt.txt 等）。
- 新增第四份母模板、新增根目錄檔案、調整資料夾結構。
- 更動 `治理/` 各檔的判準本身（門檻數字、升降級規則）——這些是制度核心，漂移成本最高。

**永遠不改**：`000.txt`、`Prompt.txt`、根目錄 `迴圈工程使用說明.txt`、`99-已總結歸檔/` 既有內容。

## 2. 改檔標準程序

1. 備份：改任何既有檔前，複製原檔到 `99-已總結歸檔/備份-YYYYMMDD-<簡述>/`。
2. 修改。
3. 若動了 `CLAUDE.md` 或 `AGENTS.md`：整檔複製到另一份，然後驗證——
   - PowerShell：`(Get-FileHash "CLAUDE.md").Hash -eq (Get-FileHash "AGENTS.md").Hash` 應回 True
   - Bash：`diff CLAUDE.md AGENTS.md && echo SYNCED`
4. 若動了三份母模板的共用塊：跑 §3 的同步檢查。
5. read-back：由 fresh-context agent 重讀改過的檔，確認引用的路徑與章節都存在（對齊 `治理/MODEL-DISPATCH.md` §5）。無 subagent 能力的環境（如 Codex solo）允許自驗，但回報必須標明「本輪 read-back 為自驗」。
6. 回報用 CLAUDE.md 的回報格式（含未動檔案清單）。

## 3. 跨檔共用塊的同步機制（SYNC-BLOCK）

三份母模板刻意重複的共用塊（完成層級階梯、主張→最低證據表、第一性原理三問/四問、反膨脹決策階梯）是本庫最大的漂移風險。機制：

- 每個共用塊在每份檔案中，起訖各加一行 HTML 註解標記：
  `<!-- SYNC-BLOCK: <塊名> v<N> -->` 與 `<!-- /SYNC-BLOCK: <塊名> -->`
- 改任何一份裡的共用塊：版本號 +1，然後把新內容與新版本號套到其他份。
- 檢查指令（任何弱模型都能跑）：只對根目錄三份母模板 grep `SYNC-BLOCK:`（**排除 `99-已總結歸檔/`**——裡面的備份副本是舊版本，命中是正常的，不要去「補齊」唯讀歸檔區）。同名塊的版本號必須一致；不一致 = 有人改了沒同步，以版本號最大的那份為準補齊。

**現況（2026-07-03）**：標記尚未加上。這是已登記的待辦（見 `治理/LETTER-TO-FUTURE-SESSIONS.md` 交接區）；在標記加上之前，改共用塊的人要手動打開三份檔案逐一同步。

## 4. 教訓回灌格式

從實戰專案把新教訓寫回母模板時：

- **先過門檻**：這條教訓能降低誤判 / 誤報完成 / 資料污染 / 重構破壞 / debug 失控 / 上下文漂移嗎？都不能就不收（心得、感想、通用口號不收）。
- **選檔**：協作行為 → LESSONS；開工流程 → SDD-WORKFLOW；UX/UI → UX-UI-PRINCIPLES；調度與驗收制度 → `治理/` 對應檔。
- **格式**：一條教訓 = 具體情境（何時觸發）+ 規則（做什麼 / 不做什麼）+ 一個實際案例。寫成「遇到 X 時，做 Y，因為 Z 曾發生」，不寫成「應保持謹慎」。
- **去重**：寫入前先搜尋目標檔，已有同義規則就強化原條目（補案例），不新增重複條目。

## 5. 長度預算與精簡觸發

| 檔案 | 預算上限 | 超過時 |
| --- | --- | --- |
| `CLAUDE.md` / `AGENTS.md` | 每 session 自動載入，最貴。上限 10KB | 抽內容到 `治理/` 或母模板，只留路由 |
| `治理/` 各檔 | 各 12KB | 先刪正反例以外的解釋段，再刪重複 |
| 三份母模板 | 各 40KB | 提清單給使用者選刪（規則刪除需授權） |

精簡的固定順序：先刪泛用口號 → 再刪重複段落 → 再刪過時歷史（案例已不可能再發生的）→ 最後才考慮合併規則。每 3-6 個月或重大專案結束後檢視一次。

## 6. 制度本身的健康檢查

每次大型維護（動超過兩個檔）結束前自問：

1. 這次改動讓「下一個弱模型 session」的第一步更清楚，還是更模糊？
2. 新增的每條規則有沒有觸發條件與判準？沒有的就是口號，刪掉。
3. 有沒有規則互相打架？（最常見：新調度規則 vs 舊 LESSONS 條文。衝突時新者標明「取代 §X」，舊者加一行指向。）
