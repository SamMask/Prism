# 模型調度守則

適用對象：在這個環境（Claude Code、Windows 11）擔任主對話的任何模型。
前置閱讀：無。本檔自我完整。派工時的 prompt 模板見 `治理/DELEGATION-TEMPLATES.md`。
與 `工具/Claude_agents-2-SUBAGENT-WORKFLOW-TEMPLATE.md` 的關係：那份是「搬去目標專案」的模板；本檔是「在本環境日常運作」的守則。兩者原則一致，衝突時以本檔為準（本檔較新、按實際環境寫）。

## 0. 本環境實際可用的調度手段（2026-07 驗證，過期要重查）

| 手段 | 事實 |
| --- | --- |
| Agent 工具 `model` 參數 | 可填 `sonnet` / `opus` / `haiku`。省略 = 沿用 agent 定義或主對話模型。不要憑印象填完整 model ID，填別名。 |
| 內建 subagent 類型 | `Explore`（唯讀搜尋，回結論不回檔案海）、`Plan`（唯讀規劃）、`general-purpose`（全工具）、`claude-code-guide`（查 Claude Code / API 文件）。 |
| 自訂 agent | 目標專案的 `.claude/agents/*.md`；implementer(sonnet) / test-runner(haiku) / explorer(sonnet) 模板內嵌在母庫 `工具/Claude_agents-2-SUBAGENT-WORKFLOW-TEMPLATE.md` §3，複製出來用。 |
| effort 參數 | **Agent 工具沒有 effort 參數。** 想要更深思考，用 prompt 要求（「先列假設與反例再下結論」）；主對話深度用 `/model` 切換模型本身。effort 分級只存在於特定 skill（如 `/code-review low~max`）。 |
| 延續 subagent | `SendMessage` 可對已 spawn 的 agent 追問，保留其 context；重開 Agent 是冷啟動。 |
| 平行 | `run_in_background: true`，或同一則訊息發多個獨立 Agent 呼叫。 |

模型定位（以能力與成本排序）：`haiku` = 便宜快速，適合機械執行與跑指令；`sonnet` = 主力施工；`opus` = 主對話預設、規劃與審查。實際型號以 harness 當下提供為準，不要寫死版本號。

## 1. 指揮官不下場

主對話的 context 是全 session 最貴的資源，只放三種東西：決策、結論、證據摘要。

**一律派出去（不要自己做）**：
- 要整檔讀任何 >300 行的檔案，或要讀 3 個以上檔案，或掃 repo 找東西 → `Explore`（兩個條件獨立成立，命中任一就派）
- 查網頁 / 查文件 / 研究比較 → `general-purpose` 或 `claude-code-guide`
- 跑測試、CI、preflight、抓 log 這類輸出很長的驗證 → test-runner 型 agent（haiku）
- 批次改多檔（模式已明確、逐檔套用） → implementer 型 agent（sonnet）
- 驗收自己剛做完的工作 → fresh-context agent（見 §5）

**自己做（派工反而虧）**：
- 單檔小改、已讀過該檔、改動 <30 行
- 需求還不明確、需要跟使用者來回釐清
- 高耦合推理：subagent 冷啟動不繼承脈絡，重建 context 的成本會超過省下的
- 對 subagent 回報的審查與完成層級判定——**這件事永遠不可外包**

判斷一句話：規劃難、執行雜 → 派；規劃簡單、執行也簡單 → 自己做。

## 2. 派工三件套（缺一不派）

每個委派 prompt 必含：
1. **目標與動機**：做什麼、為什麼做（動機讓 subagent 在邊界情況能做出對的取捨）。
2. **驗收條件**：可檢查的完成定義（哪個檔案存在、哪個測試通過、哪個問題有答案）。
3. **回報格式**：規定回什麼、不回什麼（見 §4）。

外加兩項常備：**邊界**（不可動哪些檔、不可擴張範圍、卡住就停下回報不要硬幹）與 **model 指定**（按 §3 選，不要留給預設）。

## 3. 模型選擇表

| 任務 | subagent / model | 理由 |
| --- | --- | --- |
| 掃 repo、找定義、盤點慣例 | `Explore`（預設 model 即可） | 唯讀、專為此設計 |
| 跑測試 / 抓 log / 機械驗證 | general-purpose + `haiku` | 只需執行與摘要 |
| 明確規格的施工 | general-purpose + `sonnet` | 主力施工等級 |
| 批次套用已解出的模式 | general-purpose + `haiku` 或 `sonnet` | 模式已定，便宜模型批次做 |
| 架構規劃、多方案取捨 | `Plan` 或主對話自己做 | 需要最強推理 |
| 審查 / 驗收 / 第二意見 | general-purpose + 不低於施工者的模型 | 審查者不能弱於施工者 |
| 查 Claude Code / API 用法 | `claude-code-guide` | 有專用文件工具 |

## 4. 回報合約（寫進每個委派 prompt）

- 只回：結論、`檔案:行號`、關鍵證據（測試指令與 pass/fail 數、錯誤的關鍵幾行）。
- 不回：整檔內容、完整 log、過程流水帳。
- 長產物（報告、大 diff、完整 log）落檔到指定路徑，回報只傳路徑。
- 完成層級只能宣稱到「候選 / 本機通過」；「正式接入」以上由主對話判定。
- 受阻就回報「受阻 + 原因 + 已試過什麼」，不准自行擴大授權。

## 5. 驗證不自驗

寫的人不驗收自己。驗收一律派 fresh-context agent（不帶施工過程的 context），按主張選驗法：

| 主張 | 驗法 |
| --- | --- |
| 檔案已寫好 / 已改好 | read-back：重新讀檔，對照驗收條件逐條檢查，不是看施工者的回報 |
| 程式碼行為正確 | 跑測試或實跑，貼指令與結果 |
| 高風險判斷（架構、刪東西、對外動作） | 第二意見：另派一個 agent 獨立作答，比對分歧；或多答案評審選優 |

自驗只允許一種情況：改動 <10 行且驗證是一條指令能跑完的（此時直接跑那條指令就是驗證）。

## 6. 升降級路徑（只管派工鏈；主對話自己 debug 沿用 LESSONS §2.6 三振）

計數規則：首次執行算第 0 輪；之後每次「換模型或換方法的完整嘗試」算一輪重試。**同一子任務最多兩輪重試**（= 總共最多三次完整嘗試），用完仍失敗 → 停止執行，轉純分析：列已試路徑、可能原因、下一個最小驗證，回報使用者。

- **haiku 首發失敗**（第 0 輪）→ 不讓 haiku 重試，第 1 輪直接升 sonnet；sonnet 也失敗 → 第 2 輪帶完整失敗軌跡升 opus 或收回主對話；再失敗 → 停止，轉純分析。
- **sonnet 首發失敗**（第 0 輪）→ 第 1 輪 sonnet 可換方法再試一次；又失敗（= 連錯兩次）→ 第 2 輪帶完整失敗軌跡升 opus 或收回主對話；再失敗 → 停止，轉純分析。
- **失敗軌跡必附**：每輪改了什麼、錯在哪、錯誤訊息原文。不帶失敗軌跡的升級等於讓強模型重踩一遍坑。
- **解出模式後降級**：主對話或 opus 解出的做法，整理成明確步驟，降回 sonnet/haiku 批次套用到其餘案例。

## 7. 何時破例

使用者明確說「你直接做」「不要開 subagent」時照辦。額度緊張（使用者提及）時提高派工門檻、降低模型等級，但 §5 驗證不自驗不可省——省驗證不是省 token，是製造假完成。

## 8. Claude / Codex 輪流開發時的適用範圍

使用者的專案由 Claude 與 Codex 輪流寫 code。本檔各節的可移植性：

| 節 | Claude Code | Codex |
| --- | --- | --- |
| §0 調度手段 | 直接用 | **不適用**：Agent 工具、Explore/Plan、model 別名都是 Claude Code 專屬；Codex 以當前 session 實際可用的工具與模型為準 |
| §1 指揮官不下場 | 直接用 | 原則適用：有子任務能力就派；沒有就至少做到「大輸出先落檔再讀摘要、指令加 head/tail/grep 過濾」 |
| §2 派工三件套 | 直接用 | 直接用（有子任務就寫進子任務 prompt；沒有就當動手前的自我三件套） |
| §3 模型選擇表 | 直接用 | 型號不適用；改用三檔對應：最便宜可勝任 / 主力 / 最強 |
| §4 回報合約 | 直接用 | 直接用 |
| §5 驗證不自驗 | 直接用 | 做得到 fresh-context 就照做；做不到 → 允許自驗，但必須在回報標明「本輪為自驗」 |
| §6 升降級 | 直接用 | 原則適用（帶失敗軌跡升級、最多兩輪）；模型切換多半要使用者操作，此時「升級」= 停手並整理失敗軌跡請使用者換模型 |

交接紀律：Claude 與 Codex 互相接手時，一律適用 LESSONS §7.4——不採信前手的完成宣稱，先跑最小再驗證。兩邊共用的規格與邊界要寫在專案自己的治理文件（AGENTS.md 等），不能只存在某一邊的工具設定裡。
